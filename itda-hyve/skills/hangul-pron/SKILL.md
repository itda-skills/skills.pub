# hangul-pron — 외국어 → 한글 발음 표기

외국어를 **소리 나는 대로 한글로** 적는다. 목표는 정확한 음성 표기(IPA)가 아니라, 학습자가
**보자마자 입으로 낼 수 있는** 근사치다. 정확하지만 못 읽는 표기보다 조금 틀려도 바로 읽히는
표기가 낫다.

지금 되는 것은 **영어(철자 입력)** · **중국어(병음 입력)** · **일본어(가나 입력)** 다.

```bash
node scripts/transcribe.mjs "Let's get dressed."
# → 레츠 겥 드{레=^}스드
node scripts/transcribe.mjs "The father is very careful."
# → {더=~} {빼=o}{썰=^~} 이즈 {뻬=o}{러=^} 케{얼=^}{뿔=o}.

node scripts/zh.mjs "Wǒmen chī fàn ba."
# → {워=3}먼 {츠=1#} {판=4o} 빠.
node scripts/zh.mjs "Nǐ hǎo."
# 병음(변화 후) ní hǎo.
# → {니=2} {하오=3}.

node scripts/ja.mjs "ごはんを たべよう。"
# → {고=v}항 오 타{베=v}요ー.
```

이 스킬은 `~/.claude/skills/` 에 심볼릭 링크로 연결해 쓴다. 링크는 플러그인 폴더의
`link-skills.sh` 가 만든다(`./link-skills.sh --dry-run` 으로 먼저 확인).

출력은 마크업 문자열이다. `{글자=기호코드}` 는 그 글자 위에 기호를 얹으라는 뜻이다.

| 코드 | 기호 | 대상 | 발음 지시 |
| --- | --- | --- | --- |
| `^` | ˇ | R | 혀를 뒤로 말아서 |
| `o` | ˚ | F · V | 윗니를 아랫입술에 |
| `~` | ˜ | Th | 혀끝을 이 사이에 |

## 왜 이런 구조인가

교재 784문장을 측정해서 얻은 두 사실이 설계를 정했다. **이 두 가지를 모르면 잘못된 방향으로
고치게 되므로 먼저 읽어야 한다.**

### 1. 한글에서 출발하면 안 된다

기호를 받는 음절 106종 중 **42%가 같은 음절인데 기호가 갈린다.**

```
레: ˇ×30 · ˜×1 · 무표기×155   ← "레츠"(Let's, r 없음) vs "그레ˇ잍"(great, r 있음)
브: ˚×38 · 무표기×23
```

같은 `레`라도 어느 영어 소리에서 왔는지에 따라 기호가 갈린다. 즉 **한글만 보고는 기호를 정할
수 없다.** 그래서 영어에서 출발해 한글을 만들면서 기호를 같이 붙인다. "한글을 먼저 만들고
나중에 기호를 붙이는" 구조는 원리적으로 실패한다 — 그 방향으로 고치지 말 것.

### 2. 교재 재현이 목표가 아니다

**따르는 것은 교재의 표기 철학이지 교재의 문자열이 아니다.** 교재는 같은 문장을 다르게 적기도
한다 — 중복 46종 중 17%가 그렇다.

```
hold the railing  →  뤠ˇ일링   |  레ˇ일링
no hitting        →  노 히딩   |  노 히링     (플랩 적용/미적용)
step up           →  스뗖 업˚(스떼펖˚) | 스떼펖   (기호 유/무)
```

저자 재량의 축약도 있다(`last`→라쓸, `behind`→비하인). 어느 쪽도 틀린 게 아니지만 규칙은
한쪽만 낼 수 있다. 그래서 **교재와의 문자열 일치는 목표가 아니라 참고 지표**이고, 정본 지표는
**SPEC 규칙(E1~E8 + 기호) 준수**다.

## 파이프라인

```
영어 문장
 → ① 예외 사전(LEX) 조회        ← 빈도 상위어·관용 표기·연음형
 → ② 없으면 G2P                 ← CMUdict 조회 → 철자→음소 규칙 → 옛 철자 폴백
 → ③ 연음 결합                  ← put it in → 푸리린 (SPEC 원리 5)
 → ④ 기호 부착                  ← ①② 에서 소리를 알 때 같이 붙인다
```

**규칙을 예외에 맞춰 비틀지 않는다.** 한 곳을 맞추면 다른 곳이 깨진다. 안 맞는 단어는 규칙을
고치지 말고 `LEX` 에 등록해 쌓는다.

## 기호가 핵심이다

한국어 화자가 약한 소리는 **R · F/V · Th** 다. 한글로만 적으면 이 셋이 전부 뭉개진다
(`right`·`light` 둘 다 "라잍", `fan`·`pan` 둘 다 "팬"). 그래서 이 스킬은 한글 표기보다
**기호를 빠뜨리지 않는 것**을 우선한다.

두 가지가 여기서 나온다.

**① 한 글자에 기호 두 개를 허용한다.** SPEC 원리 3 의 슬롯 모델대로 TOP(ˇ)과 AFTER(˚·˜)는
같이 붙을 수 있다. `first` 는 f 와 r 이 한 음절에 겹치므로 `{뻘=^o}`, `together` 는 th 와 r 이
겹치므로 `투게{덜=^~}` 다. 교재는 이런 자리에 기호를 하나만 찍지만, 그러면 학습자가 둘 중
하나를 놓친다.

**② 연음해도 기호를 잃지 않는다.** `give it` 은 v 가 뒤 음절로 넘어가는데, 넘어간 자리에
기호도 같이 실어야 한다 — `기{빝=o}`. 사전의 연음형은 `'ㅂ|o'` 처럼 넘길 소리와 기호를 함께
적는다.

## 성능

### 정본 지표 — SPEC 규칙 준수

```bash
node scripts/check-spec.mjs      # 실패하면 0 이 아닌 코드로 끝난다
```

E1~E8 과 기호·연음을 각각 검사한다. 문자열 일치가 아니라 **규칙의 결과가 나타나는가**로 본다
(예: E1 은 `step` 의 t 가 ㄸ 로 났는가를 자모 단위로 확인).

| 규칙 | 내용 | 통과 |
| --- | --- | --- |
| E1 | s 뒤 p·t·k → 된소리 | 5/5 |
| E2 | 모음 사이 t·d → ㄹ | 4/4 |
| E3 | 어말 파열음 → 받침 | 3/3 |
| E4 | 어말 l → 을 | 3/3 |
| E5 | 약세 -er/-or/-ar → 얼ˇ | 3/3 |
| E6 | -ing → 잉 | 2/2 |
| E7 | 강세 없는 모음 → ㅓ | 2/2 |
| E8 | 굳어진 축약형 | 3/3 |
| 기호 | R·F/V·Th (겹칠 때 둘 다) | 6/6 |
| 원리5 | 연쇄 연음 | 2/2 |
| **계** | | **33/33 (100%)** |

기호 재현율도 교재 784문장 전량에서 **R·F·V·Th 모두 100%** 다. 교재(88.6/97.3/93.4%)보다
높은데, 사람이 손으로 적으면 빠뜨리는 자리가 생기기 때문이다.

> 재현율 분모는 **겹자를 접어서** 센다 — `off` 는 ff 지만 소리는 하나라 ˚ 하나, `carrot` 도 rr 이지만
> ˇ 하나다(교재로 확인). 접지 않으면 분모가 부풀어 재현율이 실제보다 낮게 나온다.

### 참고 지표 — 교재와의 일치도

목표가 아니지만 회귀 감시용으로 둔다. 훈련 80% / 평가 20% 홀드아웃 기준이며, 평가 셋은
사전 채굴에 한 번도 쓰이지 않은 157문장이다.

| 구성 | 평가 셋 | in-domain |
| --- | --- | --- |
| 철자 폴백만 (v0.1.0) | 34.4% | 35.5% |
| + 사전 자동 채굴 | 37.6% | 53.4% |
| **+ G2P 폴백 (v0.2.0)** | **51.0%** | **51.9%** |

**여기서 얻은 교훈이 설계를 정한다.** 코퍼스 어휘 618종 중 **51%가 딱 한 번만 등장**한다.
사전은 "본 단어"에만 들으므로 아무리 키워도 새 문장에는 +3.2pp 뿐이다(채굴 +17.9pp 중
대부분이 암기였다 — 홀드아웃으로 드러났다). 반면 처음 보는 단어를 근사하는 **G2P 는 +16.6pp**
를 준다. 일반화의 지렛대는 사전이 아니라 폴백이다.

## 의존성 — CMUdict

`data/cmudict.dict` (3.6MB, 126,052 항목, BSD-2-Clause). 파일 하나를 직접 두는 방식이라
pip·npm 이 필요 없다. 첫 조회 때만 읽고(약 84ms) 이후 메모리에 상주한다(약 140MB).
파일이 없거나 깨져도 철자 규칙으로 자동 폴백하므로 동작은 계속된다.

교재 어휘 618종 중 615종(99.5%)·토큰 99.9%를 덮는다. 배포 용량이 부담이면 사전 없이
철자 규칙만으로도 평가 셋 47.8% 다(G2P 51.0% 대비 -3.2pp).

## 중국어 — 병음 입력 (v0.4.0)

```bash
node scripts/zh.mjs "Tài hǎo chī le!"     # → {타이=4} {하오=3} {츠=1#} 러!
node scripts/zh.mjs "Nǐ hǎo." --no-sandhi # 성조 변화를 끄고 사전형 그대로
```

입력은 **한자가 아니라 병음**이다. 한자에서 병음을 얻으려면 사전이 필요하고 다음자(多音字)가
따라오는데, 그건 2단계다. 병음만으로도 3언어 앱 데이터 76건이 이미 병음 필드를 갖고 있어
즉시 검증된다.

파이프라인은 영어와 같은 골격이고 **소리를 얻는 경로만 다르다.**

```
병음 → ① 음절 분리 → ② 성조 변화(C7~C10) → ③ 성모·운모 → 한글 + 기호
```

| 코드 | 기호 | 대상 | 발음 지시 |
| --- | --- | --- | --- |
| `1`·`2`·`3`·`4` | ˉ ˊ ˇ ˋ | 성조 (TOP) | 기호 모양대로 올리고 내린다 |
| `#` | ˘ | zh·ch·sh·r | 혀를 말아 올려서 |
| `o` | ˚ | f | 윗니를 아랫입술에 |
| `u` | ¨ | ü | 입술을 동그랗게 |

**여기서 틀리기 쉬운 세 가지** — 전부 실측으로 확인된 것이다.

**① 병음을 공백으로 자르면 안 된다.** `wǒmen` 같은 두 음절 낱말이 한 덩어리로 세어지면 음절
정렬이 통째로 어긋난다(검사기 오탐 49건 중 44건이 이 탓이었다). 성모+운모로 앞에서부터
최장일치로 자른다(`pinyin.mjs`). 소비하지 못한 글자는 버리지 않고 `rest` 로 보고한다 —
조용히 버리면 오타·얼화가 사라진 채 검증을 통과한다.

**② 성조는 글자가 아니라 음절 덩어리에 얹는다.** `hǎo` 는 한글로 두 글자지만 한 음절이라
`{하오=3}` 이지 `{하=3}오` 가 아니다. **이것이 중국어 표기의 핵심이다.**

**③ 경성 음절도 C1 대상이다.** `的 de` → 떠, `个 ge` → 꺼. 성조가 없다고 건너뛰면 실제 위반을
놓친다(3언어 앱에 그렇게 4건이 숨어 있었다).

성조 변화(C7~C10)는 기본으로 켜져 있고 **사전형에만 발화**하므로 이미 변화가 적용된 병음을
넣어도 아무 일이 일어나지 않는다(멱등). SPEC §2-2 총칙대로 **병음 줄도 변화 후로** 낸다 —
한글과 병음이 다른 소리를 가리키면 학습자가 혼란스럽다.

### 성능 (중국어)

```bash
node scripts/check-spec-zh.mjs                 # 정본 지표 — C1~C10 + 기호 + 병음 줄
node scripts/eval-zh.mjs [data.js 경로]        # 참고 지표 — 3언어 앱 데이터와 문자열 대조
```

| 층 | 내용 | 결과 |
| --- | --- | --- |
| 정본 | SPEC C1~C10·기호·덩어리 성조·병음 줄 | **43/43 (100%)** |
| 콘텐츠 | 3언어 앱 검사기(`check-data.mjs`)에 생성 출력을 넣어 검사 | **위반 0건** |
| 참고 | 앱 데이터 76건과 문자열 일치 | 문장 96.1% · 덩어리 99.7% |

남은 3건은 **저자 재량**이라 규칙으로 옮기지 않았다(함정 2) — 띄어쓰기를 병음 낱말 경계가
아니라 뜻 단위로 붙인 것 2건(`Bāng bang` → 빵빵, `yí biàn` → 이삐엔), `piàoliang` 의 iang 을
량으로 줄인 것 1건(같은 데이터의 `xiǎng` 은 시앙이다 — 데이터 자체가 갈린다).

## 일본어 — 가나 입력 (v0.5.0)

```bash
node scripts/ja.mjs "ちょっと まって。"     # → 촛토 맛테.
node scripts/ja.mjs "がっこうへ いこう。"   # → {각=v}꼬ー 에 이꼬ー.
```

입력은 한자 혼용문이 아니라 **가나**다. 한자에서 요미(읽기)를 얻으려면 형태소 분석이 필요하고,
그건 2단계다.

| 코드 | 기호 | 대상 | 발음 지시 |
| --- | --- | --- | --- |
| `v` | ˚ | 탁음 が·ざ·だ·ば행 | 목을 울려 부드럽게 |
| — | `ー` | 장음 | 앞 소리를 한 박자 길게 |
| — | ㅅ받침 | 촉음 っ | 숨을 한 박 멈춰 |

**여기서 틀리기 쉬운 네 가지.**

**① 모라는 글자와 일대일이 아니다.** 요음(きゃ)은 두 글자가 한 모라고, 촉음·발음·장음은
글자가 있어도 제 소리가 없다. 가나를 글자 단위로 훑으면 여기서 어긋난다.

**② 장음은 ー 만이 아니다.** `よう`·`いい`·`せい` 처럼 모음 연속으로도 길어진다. J4 는
**길이가 뜻을 바꾼다**고 못박고 있으므로 누락이 곧 오류다. 단 `おいしい` 의 お+い 는
장음이 아니다(오이) — 앞 모라의 모음이 같아야 한다.

**③ 촉음 뒤의 진짜 경계는 "앞 받침이 무엇이냐"다.** J1 은 촉음 뒤에 어중 된소리를 적용하지
말라고 하는데, 그 예외 예시(촛토·밧테)는 둘 다 **ㅅ받침**이다. ㄱ·ㅂ받침 뒤에서는 한국어가
저절로 경음화하므로 된소리로 적는 것이 소리와 맞는다(육꾸리·입빠이). 이 둘을 한 규칙으로
묶으면 한쪽이 반드시 틀린다.

**④ 조사를 뗄 때 `この` 의 の 를 떼면 안 된다.** 형태소 분석 없이 가르는 기준은 두 가지 —
`を` 는 언제나 조사라 무조건 떼고, 나머지(は·が·に·の·へ·から)는 **앞에 2모라 이상 남을 때만**
뗀다. この·その·どの 가 이 조건에서 걸러진다.

### 성능 (일본어)

```bash
node scripts/check-spec-ja.mjs                 # 정본 지표 — J1~J7
node scripts/eval-ja.mjs [data.js 경로]        # 참고 지표 — 3언어 앱 데이터와 문자열 대조
```

| 층 | 내용 | 결과 |
| --- | --- | --- |
| 정본 | SPEC J1~J8 (§2-3 예시 전량 포함) | **37/37 (100%)** |
| 콘텐츠 | 3언어 앱 검사기(`check-data.mjs`)에 생성 출력을 넣어 검사 | **위반 0건** |
| 참고 | 앱 데이터 76건과 문자열 일치 | 문장 100% (데이터를 규칙에 맞춘 뒤) |

**참고 지표가 중국어(96.1%)보다 낮은 것은 규칙이 덜 여물어서가 아니라 앱 데이터가 그 자리에서
갈리기 때문이다.** 불일치 18건은 네 갈래고, 전부 데이터 쪽이 자기 모순이거나 SPEC 이 침묵하는
자리다.

| 갈래 | 건수 | 내용 |
| --- | --- | --- |
| 어중 `て` | 9 | 규칙은 떼(J1 어중 → ㄸ), 데이터는 테. **데이터가 た·と 는 따·또로 적으면서 て 만 예외로 둔다**(9:1) |
| 종조사 `ね` 분리 | 5 | 데이터가 て형 뒤에서는 떼고(시테 네) 의지형 뒤에서는 붙인다(네요ー네) — 기준이 없다 |
| `ちゃ` | 2 | 규칙은 차, 데이터는 챠. 같은 데이터가 `ちょ` 는 초, `じょ` 는 조로 적는다 |
| 그 외 | 2 | `だ` 단독 분리(`よるだ` 요루 다 / `いやだ` 이야다 — 데이터가 갈린다), 복합어 분리 |

**어중 `て` 는 SPEC v1.3 에서 정리됐다.** 예전 J1 은 "어두 か·た행 → ㅋ·ㅌ, 어중 → ㄲ·ㄸ"
라고만 하고 **た행 예시를 하나도 주지 않아**(예시 셋이 전부 か행), 생성물이 실제로 갈렸다 —
어중 `て` 10건은 외래어 표기법 쪽(테)으로, `た`·`と` 는 SPEC 쪽(따·또)으로. **두 규범 어느
쪽과도 일치하지 않는 혼입**이었다. SPEC v1.3 이 た행 예시(`たべて` 타베떼 · `みつけた`
미츠께따)와 "어두 = 발음 낱말의 첫머리" 를 명시해 그 여지를 없앴다.

**이것은 "SPEC 정합성을 위한 정규화"이지 "떼가 음성학적 정답"이라는 뜻이 아니다.**
제2 의견(gpt-5.6-sol) 검토에서 확인된 한계를 그대로 적는다.

- 비어두 `て` 10건은 **전부 동사 `-て`형**이라, 이 표본만으로는 "가나 `て` 예외"와
  "문법형 `-て`를 익숙한 테로 적는 관행"을 **구별할 수 없다**. 독립 형태로는 8개다.
- 반례로 든 `みつけた`(따) / `できました`(타)는 깨끗한 최소대립이 아니다 —
  `/maɕita/` 의 `/i/` 는 무성자음 사이라 **모음 무성화 환경**이다.
- 한국어 청자 실험에서 일본어 **어중** 무성 파열음은 경음·격음 양쪽으로 갈린다
  (어두는 압도적으로 격음). "한국인 귀에 어중이면 된소리"는 연구보다 강한 일반화다.
- 다만 `-て`만 다른 음소·이음이라는 직접 근거도 **확인되지 않았다**. 정확한 판정은
  "음성학적 근거 없음"이 아니라 **"직접 비교 근거 미확인"** 이다.

`よく`(요꾸)·`マイクラ`(마이꾸라)처럼 **형태소·복합어 경계의 か행은 원본에서도 된소리**라,
"경계가 어두를 되살린다"는 설명은 か행에서 성립하지 않는다. 어느 가설이든 예외는 결국
`た`행 전용이 된다. 그리고 그 표기를 만든 것이 사람이 아니라 **이전 세대 생성 과정**이므로,
"저자의 판단을 보존한다" 는 선택지는 없다. 바꿀 근거가 생긴다면 그것은 문자열 대조가 아니라
**읽기 실험**이다 — `타베테/타베떼` 를 한국인이 읽은 소리를 일본어 모어 화자가 평가하는 것.

## SPEC 밖 — 생성기 정책

**이 스킬은 SPEC 의 구현체지만, SPEC 이 침묵하는 자리에서는 스스로 정한 정책이 있다.**
아래는 SPEC 에 없다 — 데이터와 어긋나면 "SPEC 위반"이 아니라 **정책 차이**다.
(`ㅈ·ㅊ` 뒤 반모음 생략과 조사 분리 기준은 v1.3 에서 SPEC J8·J6 으로 올라갔다.)

| 정책 | 내용 | 근거 |
| --- | --- | --- |
| 종조사 `ね` | 떼지 않는다 | `~てね` 는 한 호흡. 생성물은 て형 뒤는 떼고 의지형 뒤는 붙여 기준이 없었다 |
| `だ` 분리 | `だよ`·`だね` 로 끝날 때만 | 지정사 だ 는 앞말과 호흡이 끊기지만, だ 하나로 판정하면 `からだ`·`あいだ` 까지 떼게 된다 |
| 문장부호 뒤 공백 | `だ！にげて！` → `다! 니게떼!` | 한국어 조판 관례 |
| 장음 범위 | `よう`·`いい` 외에 `えい` 도 장음 | 일본어 교육 표기 관례. SPEC J4 는 "장음은 ー" 만 말한다 |

띄어쓰기가 전혀 없는 긴 입력은 **1단계의 범위 밖**이다 — 발음 낱말 경계를 알려면 형태소
분석이 필요하고, 그것이 2단계다.

## 검수 — 원어민 없이 어디까지 확인했나

원어민 감수가 불가능한 조건에서, **사람 판단 없이 확인할 수 있는 것을 층으로 나눠** 재고
나머지는 한계로 적어 둔다. 아래 셋 다 `scripts/` 에 재현 가능한 형태로 있다.

### ① 원천 데이터 — 병음·로마자가 맞는가 (사전 대조, 가장 강한 증거)

그동안의 검사는 전부 "한글이 병음·가나와 맞는가" 만 봤다. **병음 자체가 그 한자의 올바른
읽기인지는 아무도 보지 않았다** — 병음이 틀리면 이 생성기는 그 틀린 병음을 충실하게 한글로
옮기고 세 층을 전부 통과한다.

```bash
node scripts/verify-pinyin.mjs --python ~/.venv/bin/python   # 한자 → pypinyin → 데이터 병음
node scripts/verify-romaji.mjs                               # 가나 → 로마자 → 데이터 로마자
```

| 검사 | 결과 |
| --- | --- |
| 중국어 병음 (76건) | **읽기 불일치 0건** · 성조 오류 1건 발견·교정(`苦力怕` kù → kǔ) · 경성 처리 14건(정상) |
| 일본어 로마자 (76건) | **불일치 0건** |

여기서 **생성기 버그도 잡혔다** — 어휘 성조 변화가 동음자에 오발화했다(`衣 yī` 가 一 규칙에
걸려 yì 로). C8·C9 는 이제 기본으로 끈다(아래 "SPEC 밖 정책" 참조).

### ② 음성 폐루프 — 이대로 읽으면 알아듣는가

```bash
node scripts/verify-loop.mjs --lang ja --python ~/.venv/bin/python
node scripts/verify-loop.mjs --lang ja --ab "たべてね" --variants "타베떼네|타베테네"
```

한글 표기 → 한국어 TTS(macOS `say`) → 원어 ASR(Whisper) → 원문이 복원되는가.
ASR 이 가나를 한자로 바꿔 적는 습관은 **원어 TTS 를 같은 ASR 에 통과시킨 기준선**으로 상쇄한다.

| 언어 | 글자 F1 | 80% 이상 | 판정 |
| --- | --- | --- | --- |
| 일본어 76건 | **77.3%** | 48/76 | 유효 — 실패가 아래 두 원인에 몰려 있다 |
| 중국어 76건 | 25.7% | 7/76 | **이 방법으로는 판정 불가** (성조가 기호에 있어 TTS 가 못 낸다) |

**일본어 실패의 대부분은 표기 결함이 아니라 측정 한계다.** 저점수 항목을 갈라 보면:

- **어두 탁음**(가장 큼) — `ごはん` 고˚항 → `コアン`, `だいすき` → `タイスキー`,
  `ぼうし` → `星`. TTS 는 `˚` 를 못 읽고 한국어 어두 평음은 무성음이라 `고` 가 [ko] 로 난다.
  탁음 있음 74.7% / 없음 80.9% 로 갈린다. **사람이 기호를 보고 읽으면 이 손실은 없다.**
- **ASR 의 가타카나 표기** — `すわって` → `スワッテ` 는 소리가 정확한데 F1 은 0% 다.
- **장음을 모음 반복으로 TTS 에 넘긴 것** — `요ー` 를 "요오" 로 읽히니 `ようう` 로 들린다.
  사람은 길게 한 소리로 읽는다.

**측정 방법으로 설명되지 않는 진짜 후보는 3건뿐이다** — `くつを`(쿠츠 → くち),
`ほんを よもう`(홍 오 → ほんご — ㅇ받침 뒤 연음), `これは`(코레 → フレ).

### ③ 규칙 준수 — 앞서 나온 33/44/37 · check-data 위반 0건

### 확인하지 못한 것 (정직하게)

- **중국어 성조의 실효성.** 성조는 기호에 실려 있어 TTS 가 낼 수 없다. 중국어 검증은
  ①(사전 대조)과 ③(규칙)에 의존하며, "성조를 이 기호로 배울 수 있는가" 는 미검증이다.
- **자연스러움.** 문법이 맞아도 실제로 안 쓰는 표현인지는 기계가 못 본다.
- **어두 탁음이 기호만으로 전달되는가.** 위 ② 의 최대 실패 원인이자, 사람 확인이 필요한 자리.

## 남은 확장 (한자 입력)

중국어 2단계는 한자→병음 사전(다음자는 빈도 기반 1순위), 일본어 2단계는 한자 혼용문의
형태소 분석이다. 둘 다 의존성을 들이는 결정이라 **측정한 뒤** 정한다.

설계와 **측정으로 확인된 함정 8가지**는 `skills/docs/specs/SPEC-HANGUL-PRON-002.md` 에 있다 —
손대기 전에 반드시 읽을 것. 모르고 들어가면 같은 함정에 빠진다(한글에서 출발하기, 교재 문자열
맞추기, 같은 코퍼스로 캐고 재기, 병음 공백 분리 등).

표기 규칙의 정본은 별도 문서(`SPEC.md` §2-1 E1~E8 · §2-2 C1~C10 · §2-3 J1~J7)에 있다. 이 스킬은 그 규칙의
구현체다.
